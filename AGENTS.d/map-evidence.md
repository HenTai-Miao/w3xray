# 地图证据断言检查单（map-evidence）

回答玩家「怎么获得 X / 打谁掉 X / 一共有几个 X」之前，按序过完全部闸门；任何一闸不过，答案写「未证实」。**规则只写机制，具体地图的单位码/物品码/内容名词一律不进规则**——附录案例按会话代号匿名（会话A-F），案例中的图名/单位名/物品名已泛化为机制描述，**不得据此预判任何具体地图**；换图后闸门逻辑不变，代入新图数据即可。

## 闸门 0：玩家状态先行（先读人、再翻图、后开口；顺序不可倒置）

推进类问题（「接下来干嘛 / 怎么打 / 出什么装备 / 怎么变强」）的强制流程：

1. **先 live 重探现状**：选中英雄、背包六格、坐标、队友、资源（live.md 强制重探同样适用）。
2. **对齐进度**：坐标对齐地图区域/章节，背包判断已拿到的档位，推断当前进度点。
3. **差集推荐**：只推荐下一步「够得着」的升级——当前区域商店有售、当前等级能刷的掉落、原料已大半到手的配方；每件标注获取路径（哪家店/哪个Boss/什么配方）。
4. **终局 BiS 只作附注**：远期目标最多一句路线图，绝不作主答案——玩家当前拿不到的成品不推。
5. **门槛核对**：推荐转职/挑战场/航线/副本前，先核对该图的等级/进度/钥匙类门槛；不满足就先给「解锁这一步」的路径。
6. **满量才许排「最强」**：大盘点必须满量枚举（闸门 2）后才允许下「最强/毕业」结论；盘点被截断过就明说「未覆盖全部」。

## 闸门 1：掉落断言前置（防「杀 NPC 掉神装」）

1. 先跑 `pack-query <pack> where <id>` 与 `pack-query <pack> drop <id>`，答案里引用其输出（含防呆结论行）。
2. 来源只认三类证据：商店货架行（usei/Sellitems）、掉落表行（单位死亡掉落）、脚本/触发奖励（CreateItemLoc / UnitAddItemByIdSwapped / 奖池 PlaceRandomItem）。
3. **单位随身物品 ≠ 会掉**：脚本在初始化里塞给 NPC 的物品是展示道具，不构成掉落证据。
4. 合成类物品：引用脚本里的合成触发（持有原料集合 → 移除原料 → 给产物）说明配方，并对每种原料再过一遍闸门 1。
8. **工具负输出不是终点**：`drop` 无关系表行时会兜底扫脚本死亡触发（`GetDyingUnit` 条件 → `PlaceRandomItem` 池），打出「⚠ 脚本死亡奖池」段——引用时保持池子 N 选 1+权重措辞；兜底未覆盖的形态（单件 CreateItem 死亡奖励、非死亡事件抽取）仍可能漏，下「无掉落」结论前先 grep 脚本里的单位四码。
5. **交互形态必须如实**：读完函数体判定形态再措辞——使用/拾取媒介触发（GetManipulatedItem）、走近 NPC 触发（RegisterUnitInRange）、逐份消耗充能（SetItemCharges/RemoveItem 单份扣）、概率产出（GetRandomInt）都不是「N 合 1 配方」；含随机掷骰的产出写成期望/概率，不写保底合成（实例形态：某图 NPC 兑换——4 份材料逐份消耗，每次小概率出高级货/中概率中档/大概率落空，被工具推断成「×4=成品」四合一）。
6. **升级链完整性以引用计数裁决**：名字带 [N/M] 不证明存在第 N+1 级——用 `pack-query refs <id>` 查：物品只有「给予/创建」引用而零「作为材料被检测/移除」引用 = 链在此终止；宣称「还能升级」前必须有消耗它的配方证据（实例形态：某图饰物名带 [1/5] 但脚本零消耗引用，就是终点）。
7. 通关/成就奖励：读完结局触发的完整函数体再下结论——奖励内容以函数内实际 CreateItem/属性修改为准。

## 闸门 2：计数满量（防「截断数错个数」）

1. 统计「一共有几个」（Boss 数/配方数/掉落点数/指令数）必须消费 grep 的**全部**匹配行。
2. grep 单次上限 250 条：超限时改窄 pattern 或按文件分片重查，直到全量到手。
3. 禁止 slice(0,N) 后直接报数；确需抽样时写「至少 N 个（抽样）」。
4. 触发器在文件里的行号顺序 ≠ 触发顺序：尾部行同样可能是关键实体，别按行号截断。

## 闸门 3：同名不同码（防「NPC 当 Boss」）

1. 单位同名不等于同一实体：先取 fourcc 对当前图的单位表查阵营/类型——中立被动=剧情 NPC（站桩、不掉落），敌对槽位=战斗实体。
2. 连续 Boss 战/挑战场常以**另一单位 ID** 重生同名 Boss：讨论「玩家看到的那个X」前先确认是哪个码。
3. 随机奖池（脚本里的 itempool 数组）是「打怪抽奖」渠道：描述成「池子 N 选 1、抽取点 M 处」，不写成固定掉落。
4. **单位分类只认字段证据**：英雄/建筑/杂兵的身份以 fourcc 家族（大写 H*=英雄序列、小写 h*/n*=单位）、基础 ID、英雄专有字段（ustr 等）、描述文本为准；**名字风格（英文名/称号/骷髅架子长得像 Boss）不构成分类证据**——把英文名带「骑士」字样的普通单位脑补成「英雄」被玩家当场抓包（「你不能乱编啊」）。说「英雄级敌人」前先过单位表字段。

## 闸门 4：实时内存的边界（防「脑补战斗」）

1. live 读数只列**带物品单位**：无物品的战斗单位不在列表里——「列表里没有」≠「场上没有」。
2. 所有者槽位计数变化只说明单位数变了，不构成「玩家正在打某 Boss」的证据；战斗状态需玩家口述或选中单位确认。
3. 游戏随时可能退出：读到未运行就明说，不用旧快照续答。

## 闸门 5：否定断言与测量前提（防「把能用的说成坏的」）

- **坐标断言必须走 `pack-query near <x> <y> [radius]`**："脚底是什么/附近有什么/最近的XX在哪"类问题，禁止手写一次性解析（两次事故：装饰物表列位猜错得出"脚下是空的"；Rect 负号带空格+区域混谈得出错误的"最近目标"——都被玩家当场纠正）。工具已做表头驱动列定位（防列位漂移）、负号带空格的字面量归一、同码装饰物聚类、所在矩形判定。


1. **部分视图里看不到 ≠ 不存在**：任何「没有 X / 从不 Y / 机制已坏」类否定结论，必须先证明所用视图的覆盖率（例：live 的 owned_units 只含带物品单位，输出已带部分视图警告），再用独立途径交叉定位（如玩家当前选中单位的坐标）后才许下笔。
2. **预测与实测不符时，先否证前提，再否证机制**：差分结果显著低于预期时，候选解释按平凡度排序（玩家正在购买中/数量没到位/时点错位）先排除，最后才轮到「作者写错了」。
3. **宣布「地图有 bug」的门槛 = 受控复现**：锁定全部前提（数量、时点、对象）后的测量仍然异常，且平凡解释全部排除，才许说设计缺陷；否则写「未复现/存疑」。
4. **测量前锁前提**：差分类实测开始前确认对象状态（数量、是否正在变动）；测量窗口内玩家可能购买/研发/出售，解读时显式排除状态突变。
5. **置信度跟随证据等级**：静态推断不得用「实锤/确认」措辞；只有内存实测或满量数据交叉咬合后才升格为定论。玩家的一手观察是实测数据，与理论冲突时按闸门 0 重测，而不是替理论辩护。

## 附录：历史案例（会话代号匿名；仅示意，规则不依赖任何具体图）

- 三连错：(a) Boss Rush 播报 grep 命中 61 条只看前 30 条，把 9 个 Boss 报成 8 个（漏的恰在被截断的后续条目里）→ 闸门 2。(b) 看到剧情 NPC（中立被动、开局生成）随身带某高级物品，断言「杀她掉顶级装」，掉落表无此记录、该回路只能合成 → 闸门 1/3。(c) 敌方槽位计数下降被脑补成「正在打该 NPC」，实际玩家早已通关 → 闸门 4。
- 玩家原话：「你这说的 boss 还有掉落全错啊」「你给我我也拿不到」。
- 修复链：AGENTS.md 两条 Knowledge 原则 + 本检查单 + pack-query drop 防呆结论行。

### 追加案例（会话B：定时产出与部分视图）

- grep 的 matches 按**行**返回（一行内多次出现只占一条），而消费侧的展示循环对该行反复切片展示，其余**命中行被完全掩盖**——据此断言「全局计数变量全图只有初始化、从未写入，收入公式是死代码」，实际另一行存在研发完成自增赋值，险些把可正常工作的机制报成设计缺陷。防御：对否定型结论（「从未」「只有」）必须按行号去重消费**全部**匹配行，且用第二种模式（如按写入语句 `set X\[` 单独搜）交叉验证后再下结论。
- 同会话第二起（更严重）：靠「带物品单位捞取列表」定位玩家的生产建筑，列表里只有 4 座预置建筑，据此断言「产出单位的计时器永不启动=0 效果」并发给玩家；实际玩家自己区域内还有一座**不带物品**的同类建筑，捞取列表根本看不见——产出单位一直满效率工作（实测速率与全部 7 只的理论值完全吻合）。教训：**部分视图（如仅含带物品单位的内存捞取）里看不到 ≠ 不存在；下「不存在/永不」结论前必须先确认视图覆盖率，用独立途径（如玩家当前选中单位的坐标）交叉定位**。
- 连带教训：**测量窗口内玩家状态在变**（探针抓到玩家正选中商店/正在购买），把「窗口内约 1 只产出单位的增速」误当「7 只终速」；差分实测前必须锁定前提（数量、时点），窗口内状态突变要在解读中显式排除。
- 优先级总则：**玩家的一手观察 > 我的机制理论**；两者冲突时先假设理论错，用内存实测裁决——本会话玩家连续三次纠正（产量没区别→确实变快→你没看内存），全部判对。
- 第三起（会话C，与前两起同族）：用**定宽非重叠**上下文正则（`.{60}关键词.{60}` 的 matchAll）枚举变量全部引用，相邻出现被已消费窗口吞掉，据此断言「计数器从未自增=作者遗留调试」；实际存在关键赋值与整套机制，与第一起（grep 按行返回被展示循环掩盖）同根＝**消费侧不完整**。防御：否定型结论（「从未/只有N处」）必须用重叠安全方式枚举（零宽 matchAll 或按行号去重），并换第二种模式（直接搜赋值语句）交叉验证。

### 追加案例（会话D：名字脑补与工具形态失真）

- 名字脑补分类：波次表里某小写 h 族单位（英文名带骑士字样）被标成「（英雄）」发出去，玩家原话「哪里是英雄啊 你不能乱编啊」；字段证据（小写 h 单位族、无 ustr、描述自称"地面单位"）全部指向普通精英怪 → 闸门 3 第 4 条。
- 工具推断的配方形态失真：guide 把「逐份消耗+概率掷骰」的某 NPC 兑换渲染成「材料×4=徽章」四合一；引用触发原文才看出是赌兑 → 闸门 1 第 5 条 + pack-query refs 工具化。
- 断链自查（未外流）：「某饰物[1/5]」差点按名字推成"还能升到 5/5"，引用计数（3 处全是给予、0 处消耗）识破终点 → 闸门 1 第 6 条 + refs 零消耗警告。

### 追加案例（会话E：坐标断言）

- 坐标断言连翻两车（玩家两连纠「我脚底下是个阵啊」「我刚刚的位置是另一个区域」）：①装饰物表按猜的列位解析 X/Y，实际列位不同，半径内清零→答"空地"；②"最近的目标"把装饰群坐标与触发矩形中心混谈且负号带空格的 Rect 字面量解析错。正解全在脚本里（聊天字触发条件 RectContainsUnit 按矩形写死）。→ 闸门 5 坐标断言 near 前置 + near 子命令（表头驱动+归一+聚类）。

### 追加案例（会话E·续：工具假阴性）

- 工具假阴性（未外流）：问「某首领掉什么」，关系表 0 行、`drop` 返回「未找到获取途径」，脚本里却是 100% 必掉奖池（`GetDyingUnit` 条件 → `PlaceRandomItem(奖池数组)`，7 件等权）——若照搬负输出就会答错「无掉落」。→ 闸门 1 第 8 条：drop 增加脚本死亡奖池兜底，负输出不作为终点。

### 追加案例（会话F：归属乱认）

- 归属乱认（玩家原话「我是蓝色啊 你不能乱说啊」）：live 归属链在本图布局学习失败（player_rows 空、owner_counts 只有垃圾值），却在无任何归属证据时把场上**队友的英雄**（带关键物品）说成「你现在的英雄」，真正的玩家单位（选中的辅助英雄）反被当路人。可用信号当时就在手里：两次探针间**该单位在移动**=玩家控制。→ 归属断言需链证据（AGENTS.md 闸⑤）+ live 归属不可读横幅（player_rows 未产出即打印，禁断言+选中位移推断法）。

# 批量图标、完整描述与装备关系提取

## Schema 6 当前契约

批量输出使用 schema 6 / extraction revision 6。输入地图、旧输出、旧缓存和客户端证据都是
只读根；新产物只写到显式选择的 v6 输出根。schema 6 把一张地图的结果拆成三条独立轴：

- **发布结果**：是否形成通过所有权、内容清单、必需报告和文件哈希验证的权威发布。
- **档案完整性**：完整、存在原始块、存在损坏块或存在受限块，不因“发布成功”而隐藏缺口。
- **知识证据完整性**：依据当前文本、图标缺口、关系部分和端点未解析单独判断完整或部分。

schema 6 另存独立的“源覆盖缺口”计数；标准对象、脚本、触发、放置和文本源均缺失时，零对象
地图不会再被误报为知识完整。该计数写入状态 JSON、每图清单、批量汇总、三轴汇总和 GUI。

单一的“完整/部分/受限”状态只作为兼容投影；`三轴状态汇总.tsv` 才是这三条轴的权威视图。

每张地图的 `对象完整描述.tsv` 保留全部文本证据，并用 `是否当前值` 标记当前选择；GUI 可在
「当前文本」与「全部证据」之间切换，不删减原始值。每张地图还必须发布 `图标未解析.tsv`，
保留规范路径、主原因、诊断标志、对象身份和引用集合，发布验证会把这些行与清单和状态计数
逐项对账。

批次根另外发布四份全局证据：

- `图标缺口汇总.tsv`：只聚合通过清单验证的逐地图 `图标未解析.tsv`。
- `图标候选绑定.tsv`：记录跨地图同路径或匿名内容哈希匹配；`是否采用` 必须为“否”。
- `图标缺口统计.txt`：按原因、命名空间、扩展名、对象分类和地图汇总。
- `三轴状态汇总.tsv`：每个输入的发布、档案和知识三轴以及精确计数。

候选只供人工排查，绝不会被采用为当前地图资源，也不会覆盖缺口记录。终止/失败输入只进入
三轴状态，不会凭未验证的地图目录制造全局图标证据。

## 图标缺失的根因与安全补全

图标链路必须分别判断“字段选择、路径绑定、载荷读取、PNG 转换、GUI 展示”。本轮确认的转换
和写出失败均为 0；原问题集中在前两层：

- 单位、物品和科技文本表中的 `Art` 曾未进入严格字段集合，辅助元数据图标也可能错误挤掉
  主图标。现在保存每个当前图标角色，但 GUI 主缩略图始终优先普通游戏界面图标。
- 技能和科技的逗号多等级 `Art` 曾被当成一个文件名；现在逐等级无损拆分，空等级保留为
  `invalid_reference`，不会再查询名为 `,` 的档案文件。
- 孤立 Unicode 代理字符等无法编码的虚拟路径曾在 MPQ 查询或磁盘路径构造时抛出
  `UnicodeEncodeError`，从而中止整张地图。现在查询和写出边界会先拒绝不可编码路径，以
  `\uXXXX` 审计形式保留原始异常值并归类为 `invalid_reference`；该对象没有图标，但地图
  继续发布为“部分完成”。
- 当前对象完全没有图标字段时，工具可读取同一源地图 SHA-256 的可信历史证据；仅当分类、
  rawcode 精确一致且历史路径唯一时采用。当前作者显式字段（包括显式空值）优先，多路径冲突
  一律拒绝，补全结果同步给证据索引和 GUI 对象图标。
- 余下 887 个具名引用没有可验证载荷，其中 382/385 个物品对象集中在受保护地图
  `E3FB7D21D2E569D3C70FACA369291FD7.w3x`。该地图能读出匿名 BLP 块，却无法证明这些块与
  `war3mapImported` 路径的对应关系。要继续闭合，只能提供该图的原始 listfile/未保护源图、
  或同一地图哈希的可验证对象绑定；其余客户端路径需要完整 Warcraft MPQ/CASC 数据或扩充
  可信客户端缓存。不得按文件名、视觉相似度或其他地图自定义资源猜测。

## 运行命令

```bash
uv run main.py description-cache migrate \
  --legacy-output <schema-1-root> \
  --legacy-cache <schema-2-cache.tsv> \
  --output <owned-cache-root>

uv run main.py batch <maps-root> \
  --output <v6-root> \
  --game-data <client-or-trusted-icon-root> \
  --description-cache <owned-cache-root>

uv run main.py integrity snapshot \
  --root maps=<maps-root> \
  --root legacy-v1=<root> \
  --root legacy-v2=<root> \
  --root legacy-v4=<root> \
  --output <before.json>

uv run main.py integrity verify --snapshot <before.json>
uv run main.py integrity retained-cache \
  --active-root <owned-cache-root> \
  --output <retained-cache-report.json>
```

`--game-data` 可指向可读的 Warcraft 客户端数据目录。经典客户端按
`War3Patch.mpq → War3xLocal.mpq → War3x.mpq → war3.mpq` 查询。历史 schema 4 验收使用由旧批次客户端
MPQ 证据构建的只读可信图标缓存；缓存中的每个虚拟路径都绑定 SHA-256、原客户端档案和同一张
源地图的引用证据，不能把其他地图的自定义图标当作客户端资源。

schema 6 只接受显式 `--description-cache` 指向的已拥有、已验证缓存 generation。迁移命令从
只读 legacy 输入构建新缓存；批处理不会从任意旧结果隐式采纳文本。GUI 也可从数据工具菜单
选择或清除可信描述缓存。缓存只接纳原版基础对象、客户端补全、键和值均唯一的记录。

`integrity snapshot` 与 `verify` 用内容和纳秒 mtime 证明只读输入前后一致。`retained-cache` 将
有意保留的 `previous`、失败 stage/output 和 recovery，与仍在发布命名空间中的 stage/backup
临时违规分开报告；它不会把保留对象加载为描述来源，也不会删除、修复或重命名它们。
完整性报告覆盖采用追加式不可变历史：新报告保持 `--output` 原路径，旧报告移入
`.w3xray-integrity-history/<输出文件名 SHA-256>/<generation-id>/`。历史代的
`report.json` 由 `历史清单.json` 绑定原文件名、大小和 SHA-256，每次覆盖只追加一代，
不会自动删除旧代。历史根名称及其目标文件系统物理别名不能作为报告输出名；交换前失败
会对仍属本次写出的 stage 做身份门控清理，交换结果不可信时保留证据。该历史策略不影响
通用地图/资源写出器的原子替换职责。

## 完整描述规则

`对象完整描述.tsv` 一行对应一个对象、文本角色、等级/变体和证据值。覆盖名称、称谓、编辑器
后缀、普通提示、扩展提示、学习提示、学习扩展提示、关闭提示、关闭扩展提示、Buff/效果提示、
复活提示、唤醒提示、编辑器描述，以及字段元数据确认的其他文本说明。所有等级逐条保留。

每条记录同时保存：

- 原始全文：保留 Warcraft 颜色代码、`|n`、制表符、CR/LF、引号、首尾空白，不限制长度。
- 可读全文：只执行确定性的颜色代码清理和换行展开，不覆盖原始值。
- 来源类型、来源文件或 WTS 字符串位置、字段键、字段标签、等级和证据序号。
- 状态、占位标志和冲突组；同优先级冲突保留全部原值。

解析顺序固定为：

1. 当前地图/战役自己的二进制对象、具名文本、SLK 和 WTS 正文。
2. 当前地图中通过静态验证的匿名文本对象块。
3. 当前 Warcraft 客户端基础对象数据。
4. 已验证且无冲突的原版基础对象可信缓存。

地图中显式零长度值会阻止低优先级补全。固定占位值会保留为证据，但允许客户端或缓存补全。
绝不使用其他地图的自定义对象说明，也不根据名称或短文本猜写描述。

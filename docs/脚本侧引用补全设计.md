# 脚本侧引用补全（jass_natives，A+B）设计

> 来源：从「魔兽ID拖入无反应解决方法」工具包随包的 `blizzard.j` / `common.j`
> （经典 ht + 重制 rb）提取**派生事实表**——native 参数类型 & BJ 用到的对象码。
> 只读分析，不复制 .j 本身（与 base_names 从游戏数据离线生成同一立场）。

承接上次的对象引用分析（[[references-feature]] / `references.py`）。上次孤立报告的弱点：
脚本里的对象引用提取不全（`scan_object_refs` 只认几个 native、只出物品/单位）。本次补全。

## B：native 参数类型 → 脚本提码提全（主要价值）
- common.j 每个 native 的参数带类型与名字，参数名编码对象类别：
  `unitid/unitId`→单位、`itemid/itemId`→物品、`abilcode/abilityId`→技能、
  `objectid`→可破坏物、`techid/techId`→科技。
- 升级 `scan_object_refs`：遍历脚本行，匹配 `NATIVE_OBJ_FUNCS` 里的 native，
  按其分类把该行的码归类。返回 `{物品/单位/技能/科技/可破坏物: set()}`（保留旧键兼容）。
- 直接让自定义技能/科技等的脚本引用提全 → 减少上次的孤立误报。

## A：BJ 隐式引用 + 地图特征洞察
- 多数 BJ 硬编码码是**基础对象**(htow/ngol/Hamg…)，基础对象本就不计孤立，故 A 的减误报作用小；
  A 的真价值是**地图特征洞察**：这张图脚本用了哪些暴雪机制。
- `scan_script_features(script)` → (检测到的特征列表, 隐式引用码集合)。

## 离线生成器 build_jass_natives.py → 烘焙 w3xtool/jass_natives.py
沿用 build_base_names.py 模式（读文件→烤成 .py、运行时零依赖）。四张表：
- `NATIVE_OBJ_FUNCS = {native名: 分类|None}`（恰好一个对象码参数→该分类；多个不同类→None）
- `BJ_FUNC_CODES = {BJ名: [codes]}`（curated 名单：各族 MeleeStartingUnits*、ChooseRandom*、中立建筑、电梯…）
- `BJ_FEATURES = {BJ名: 中文特征}`（MeleeStartingUnitsHuman→人族对战开局、ChooseRandomCreep→随机刷野怪…）
- `BJ_CODE_CONSTANTS = {bj_常量名: code}`（bj_ELEVATOR_* 等）

## 接入
- `references.build_reference_graph`：升级后的 `scan_object_refs` 全类结果 + A 的隐式码并入 orphan 的 roots。
- `api.MapData` 加 `script_features: list`；`load_map` 调 `scan_script_features` 填充。
- GUI「地图信息」标签页底部加"脚本特征"一节；CLI 打印特征。

## 测试 tests/test_jass_natives.py
- 合成脚本：`UnitAddAbility(u,'AHbz')`→技能、`CreateUnit(p,'hfoo',…)`→单位、melee BJ→特征+隐式码。
- 烘焙表非空自检（NATIVE_OBJ_FUNCS/BJ_FUNC_CODES 有内容）。

## 不做
- 不做完整 JASS AST/位置参数解析：按"native→该行码归该类"的行级启发即可（多数对象码 native 恰一个码参数）。
- 不复制 blizzard.j/common.j 进仓库，只烤派生事实表。
